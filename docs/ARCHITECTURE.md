# Архитектура Jungo

> Это целевая архитектура для обсуждения, а не описание уже существующего кода. До реализации нужно подтвердить минимальную версию macOS и технологию хранения.

## 1. Направление

- Язык: Swift.
- UI: SwiftUI.
- AppKit: точечно для возможностей, которые SwiftUI не покрывает качественно.
- Режим работы: локальный, без обязательного backend.
- Тесты: unit-тесты доменной логики и хранения; UI-тесты критических пользовательских потоков.
- Зависимости: только при явной выгоде; предпочтение системным API.

## 2. Слои

### Presentation
SwiftUI-экраны, компоненты, навигация, состояния загрузки/ошибки/пустых данных и адаптация под размер окна. UI не должен самостоятельно реализовывать правила перемещения и хранения карточек.

### Application
Команды и сценарии: создать задачу, изменить её, переместить, переставить, удалить/архивировать, экспортировать данные. Здесь координируются изменения между доменной моделью и хранилищем.

### Domain
Модели и правила:
- Board
- Column
- Task
- Label
- ChecklistItem
- TaskPriority
- идентификаторы и правила порядка

Доменный слой не зависит от SwiftUI и конкретного хранилища.

### Persistence
Интерфейс репозитория и выбранная реализация локального хранилища. Ответственность слоя: транзакционность, миграции, сериализация, резервное копирование и обработка ошибок.

## 4. Хранение данных

Кандидаты для локального хранения:
- **SwiftData** — интеграция с Apple-экосистемой и меньше инфраструктурного кода.
- **SQLite** — явный контроль над схемой, запросами и миграциями.

Выбор нельзя делать только по моде. Нужно проверить минимальную версию macOS, сложность связей и сортировки, требования к миграциям, экспорт и восстановление. Для небольшого MVP допустим самый простой вариант, если тесты подтверждают надёжность.

Независимо от выбора:
- изменения должны сохраняться атомарно там, где это возможно;
- порядок карточек должен быть детерминированным;
- ошибки записи должны отображаться и логироваться;
- формат резервной копии должен быть документирован;
- тесты миграций должны проверять данные до и после преобразования.

## 5. Перемещение карточек

Операция перемещения принимает идентификатор задачи, целевую колонку и позицию. Она должна обновлять принадлежность и порядок как одну логическую операцию. UI передаёт намерение, а доменная логика валидирует операцию.

Проверять:
- перенос в ту же колонку;
- перенос в пустую колонку;
- перенос в начало, середину и конец;
- повторный вызов операции;
- перемещение при фильтрации;
- сохранение корректного порядка после перезапуска.

## 6. Состояние и ошибки

- UI получает состояние через наблюдаемые модели/представления, соответствующие выбранному подходу.
- Источник истины для сохранённых данных — слой хранения, а не состояние конкретного экрана.
- Ошибки не должны молча теряться.
- Не сохранять дублирующиеся вычисляемые значения без необходимости.
- Системные API и зависимости скрывать за небольшими интерфейсами там, где это улучшает тестируемость.

## 7. Логирование и приватность

- Не отправлять пользовательские данные в сеть.
- Не логировать текст задач и описания по умолчанию.
- Логировать технические события и ошибки без чувствительного содержимого.
- Не добавлять аналитику до отдельного продуктового решения.

## 8. Архитектурные ограничения

Не начинать с микросервисов, аккаунтов, облачной базы или сложного DI-контейнера. Для local-first приложения это создаёт стоимость без подтверждённой пользы.
