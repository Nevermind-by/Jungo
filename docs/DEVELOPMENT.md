# Разработка и Git workflow

## 1. Правило веток

**Каждая новая функция — отдельная ветка.** Исправления и документация также группируются по смыслу, а не размазываются по десяткам мелких коммитов.

Именование:
- `feature/<short-name>` — функциональность.
- `fix/<short-name>` — исправление.
- `docs/<short-name>` — документация.
- `refactor/<short-name>` — рефакторинг без изменения поведения.

Примеры: `feature/kanban-board`, `feature/local-persistence`, `docs/project-foundation`.

## 2. Обычный цикл работы

1. Проверить состояние репозитория и актуальность `main`.
2. Сформулировать результат, критерии готовности и риски.
3. Создать отдельную ветку от актуального `main`.
4. Реализовать законченную часть работы, включая связанные тесты и документацию.
5. Запустить доступные проверки и изучить diff целиком.
6. Исправить найденные проблемы.
7. Сделать один осмысленный коммит или небольшое число логически необходимых коммитов.
8. Отправить ветку и открыть PR с описанием, тестами и известными ограничениями.
9. Проверить PR и только затем слить в `main`.
10. Убедиться, что `main` содержит ожидаемый результат; удалить ветку после слияния, если это безопасно.

Не пушить каждую мелочь. Не создавать коммиты без законченного изменения. Не менять `main` напрямую в ходе обычной разработки.

## 3. Коммиты

Предпочтительный формат:
- `feat: add board navigation`
- `fix: preserve task order after move`
- `docs: define product requirements`
- `test: cover task reordering`
- `refactor: isolate persistence repository`

Коммит должен описывать законченный смысловой результат. Не объединять несвязанные функции в один гигантский коммит.

## 4. Pull request checklist

- [ ] Изменение решает заявленную задачу.
- [ ] Нет случайных файлов, секретов и локальных артефактов.
- [ ] Проект собирается.
- [ ] Тесты затронутой логики проходят.
- [ ] Обновлена документация, если поведение или архитектура изменились.
- [ ] Проверены ошибки, пустые состояния и граничные случаи.
- [ ] UI проверен на светлой/тёмной теме и узком окне, если применимо.
- [ ] PR описывает решение, проверки и оставшиеся риски.

## 5. Definition of Done

Задача считается законченной, когда:
- критерии приёмки выполнены;
- изменения реализованы и проверены;
- данные не теряются в предусмотренных сценариях;
- документация соответствует фактическому поведению;
- изменения находятся в feature-ветке и готовы к ревью;
- после ревью и слияния подтверждён результат в `main`.

## 6. Работа с пустым репозиторием

До выбора структуры приложения не создавать множество пустых директорий и файлов-заглушек. Первый программный блок должен принести запускаемый каркас, а не только скелет будущей архитектуры.
